# コードを書いた意図

コードのコメントにも「意図」を残しています。この資料は全体のつながりと、別の方法を選ばなかった理由をまとめたものです。

## 処理の流れ

ブラウザで登録 → WebControllerが受け取る → TicketServiceが入力を確認 → TicketRepositoryがファイル保存 → 一覧へ移動 → HtmlViewsが画面を作る。

## ファイルの役割

| ファイル | 役割 | なぜ分けたか |
|---|---|---|
| App.java | 起動・クラスの組み合わせ | 起動設定と業務処理が混ざるのを防ぐ |
| Ticket.java | 問い合わせ1件のデータ | 1件の意味をまとめ、引数の取り違えを減らす |
| TicketService.java | 入力と対応のルール | 画面を変更しても同じルールを使うため |
| TicketRepository.java | 保存と復元 | 保存方法だけを後からDBに置き換えやすくするため |
| WebController.java | HTTPの受付・返信 | ブラウザとの通信を業務処理から分離するため |
| HtmlViews.java | HTMLの生成 | 表示の修正箇所をまとめるため |
| style.css | 色・余白・狭い画面への対応 | 見た目をJavaの業務ルールから分けるため |
| SupportNoteTest.java | 重要な振る舞いの確認 | 誤入力やI/O失敗を再現して確認するため |

Repository＝データの読み書きをまとめる役割。Service＝業務ルールをまとめる役割。Controller＝入力を受け取って処理を振り分ける役割。名前を覚えるより、どこで何を判断しているかを追ってください。

## Ticket.java

- `enum Status`：使える状態を3種類に限定する。自由な文字列だと表記ゆれや誤字が起きる。
- `final`：作った後に項目を書き換えない。更新時は新しいTicketを作る。
- `withProgress`：状態と対応メモだけを更新する。受付日時とIDは引き継ぐ。
- 今回は読みやすさ優先でデータ項目をpublic finalにした。実務ではprivateとgetter、record、ORM向けEntityなどの選択肢がある。

## TicketService.java

- `checkedText`：必須・空白・文字数を共通処理にする。画面のrequiredだけでは、直接送信された不正入力を防げない。
- `codePointCount`：絵文字などをJavaの文字数で数えやすくする。結合文字の見た目の数とは一致しない場合がある。ブラウザのmaxlengthとも完全には一致しない。
- `CATEGORIES`：分類を固定する。利用者が分類名を毎回考える必要を減らす。
- `create`：IDは現在の最大値＋1。再読込後も既存IDと重複しない。
- `update`：完了にする場合だけ対応メモを必須にする。未対応や対応中へ戻す操作も可能。
- `search`：大文字小文字を区別せず、件名・内容・対応メモを検索する。結果は受付の新しい順。分類そのものはキーワード検索の対象ではない。
- `synchronized`：同じServiceの更新を順番に行う。別プロセス間の同時保存を防ぐものではない。
- 一覧をコピーして更新し、保存が成功するまで元データを変えない。

## TicketRepository.java

- `Properties`：キーと値の標準形式。JSONライブラリや独自パーサーの導入を避ける。改行や記号の変換はJavaの標準処理に任せる。
- `version`：保存形式のバージョン。今後構造を変更した際に、読める形式かを判断できるようにする。
- `try (...)`：ファイルを使い終わったら必ず閉じる書き方（try-with-resources）。
- 一時ファイルに最後まで書いてから置換：保存途中で元データを壊す可能性を減らす。
- `ATOMIC_MOVE`：置換を一つの操作として行う指定。対応していない保存環境では通常置換に切り替える。絶対的な耐障害性やバックアップを保証しない。
- 壊れたファイルで起動停止：空の一覧を勝手に作り、元データを上書きする事故を防ぐ。
- `findAll`はコピーを返す：内部の一覧を他のクラスが勝手に変更できないようにする。
- データが増えると全件読み込み・全件保存が重くなる。大量データ向けにはDBへ移行する。

## WebController.java

- GET：画面を表示する操作。POST：登録・更新する操作。URLを開いただけでデータを書き換えない。
- URLデコード：フォームから届く符号化された日本語・改行を元に戻す。
- token照合：このアプリの画面を経由しない別サイトからの更新を防ぐ（CSRF対策）。認証ではない。アプリ再起動時に値が変わるため、古い画面は開き直す。
- 送信サイズ制限：極端に大きいリクエストをそのまま読み込まない。
- 303で一覧に移動：保存後の再読み込みによる二重登録を減らす（Post/Redirect/Get）。ボタンの連打による別々のPOSTまで防ぐ仕組みではない。
- 400：入力不正。403：確認用token不一致。404：対象なし。500：内部処理・保存失敗。成功したように表示しない。
- 入力エラーや保存エラー時はフォームに入力値を戻す。利用者が書き直す負担を減らす。

## HtmlViews.java / CSS

- `escape`：`<` などの特殊文字を安全な表示用に変換する（XSS＝入力を使ったスクリプト実行への対策）。
- text block：長いHTMLを読みやすく書くJavaの複数行文字列。業務処理とは別ファイルにする。
- labelと入力欄：何を入力するかを明示する。
- 状態は色だけでなく日本語でも表示：色が区別しにくくても意味が伝わる。
- エラーの `role="alert"`：画面読み上げでもエラーに気付きやすくする。
- 小さい画面では縦並び：ボタンや文章が重ならないようにする。
- CSS変数：共通の色や線をまとめて修正しやすくする。

## 今回の範囲と次の段階

学習を始めた段階で処理を追えるよう、DB・認証・外部ライブラリを省いた。代わりに登録、検索、保存、入力エラー、失敗時の振る舞いを最後まで作る。

この選択には制約もある。HTMLをJavaで組み立てるため、画面が増えると保守しにくい。保存は全件単位で、大量データや共同利用に向かない。次にSpring Boot＋テンプレートエンジン＋DBへ移行し、同じ機能を別の構成で比較する学習につなげる。
